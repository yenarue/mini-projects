# ie-build — 혁신생태계론 개념정리 사이트 빌드

Google Drive의 `개념정리/W##/*.md`를 읽어 `study/innovation_ecosystem/`에 정적
사이트(index / W##.html / quiz.html / map.html / core.html)를 생성하는 Node
빌드 도구다. 이 문서는 학기 내내(주 1회 이상) 이 도구를 돌릴 소유자를 위한
운영 매뉴얼이다 — 세부는 잊어도 이 파일만 보면 다시 돌릴 수 있게 쓴다.

## 한 줄 요약

```bash
cd ~/Developers/mini-projects/_tools/ie-build
node build.mjs --check
```

깨진 링크 없이 끝나면 `study/innovation_ecosystem`을 커밋·푸시한다. 그게 전부다.
아래는 "무엇을 언제 고쳐야 하는지"에 대한 상세다.

## 매주 하는 일 (기본 흐름)

1. Google Drive의 `개념정리/W##/*.md`에 그 주 배운 내용을 정리해 둔다(이 도구는
   그 폴더를 읽기만 한다 — 안에서 직접 만들지 않는다).
2. 빌드한다.
   ```bash
   cd ~/Developers/mini-projects/_tools/ie-build
   node build.mjs --check
   ```
3. 콘솔 마지막 줄(`요약: ...`)에서 개념·주차·이미지·퀴즈·경고 개수가 말이 되는지
   훑어본다. `내부 링크 N건 검사 / 깨진 링크 없음`을 반드시 확인한다. 깨진 링크가
   있으면 원인을 고치고(체커를 느슨하게 만들지 않는다) 다시 돌린다.
4. 경고 목록을 본다. `[related] ... 대상 개념이 아직 없습니다`류는 다음 주 개념이
   아직 안 쓰였다는 뜻으로, 대부분 정상이다(§ 알려진 사항 참고). 처음 보는 경고
   종류(`[weeks]`, `[answers]`, `[importance]` 등)가 새로 뜨면 원인이 될 수 있는
   파일(아래 § 데이터 파일 참고)을 먼저 확인한다.
5. 커밋·푸시한다.
   ```bash
   cd ~/Developers/mini-projects
   git add study/innovation_ecosystem && git commit -m "content: W## 개념 추가" && git push
   ```
   1~2분 뒤 `https://yenarue.github.io/mini-projects/study/innovation_ecosystem/`에
   반영된다.

## 새 주차가 열릴 때 (강의를 들은 뒤)

1. `weeks.json`에서 그 주차의 `lectured`를 `true`로 바꾼다. 항목이 아예 없으면
   새로 추가한다(`id`/`date`/`topic`/`subtitle`/`source`/`quiz`/`lectured`).
   `lectured: false`인 주차는 개념이 있어도 페이지가 생기지 않는다(§ 6.2 설계).
2. 교수 공지로 퀴즈 범위·날짜가 바뀌었으면 `quiz-schedule.json`을 고친다. 각
   항목은 `{ n, date, weeks: [...] }` — `weeks`는 그 회차까지 누적 범위다.
3. 그 주차에서 이전 주차와 비교할 만한 개념이 나오면 `comparisons.yml`에 표를
   추가한다(아래 § comparisons.yml 참고). map.html의 "주차 간 비교표"에 그대로
   실린다.
4. 새로 쓴 개념 각각을 `importance.json`의 `concepts`에 추가한다(5점 만점 +
   근거 한 줄). **빠뜨려도 빌드는 안 죽는다** — 대신 경고
   `importance.json에 없어 기본값 3점으로 표시합니다`가 뜬다. 이 경고가 곧
   "아직 채점 안 한 개념 목록"이니 빌드 로그에서 그대로 체크리스트로 쓴다.

## 퀴즈 모범답안 추가하기

답안 파일은 `_tools/ie-build/answers/<week>-<concept-slug>.md` 하나 = 개념
하나다(예: `answers/W01-c05.md`). 형식:

```markdown
---
week: W01
no: 5
---

## Q1
> (그 시점의 퀴즈 포인트 원문을 그대로 붙여넣는다 — 이게 "질문 스냅샷"이다)

여기에 자기 언어로 쓴 답안을 마크다운으로 쓴다. 링크(`[텍스트](../W02-1/03-*.md)`)도
쓸 수 있고, 빌드가 실제 사이트 링크로 바꿔준다.

## Q2
> ...

...
```

- `week`/`no`로 개념을 찾고, 파일명(`<week>-c<no>.md`)이 frontmatter와 다르면
  경고만 내고 계속 진행한다(일치시켜 두는 게 좋다).
- **질문 스냅샷 가드**: `>` 뒤에 붙여넣은 질문 원문을, 빌드 시점의
  `concept.quizPoints[i]`(공백·이모지 무시하고 비교)와 대조한다. **교수가 소스
  노트의 질문 문구를 고치면 스냅샷과 달라지고, 이때 빌드는 그 답안을 조용히
  숨긴다** — 잘못된 질문 아래 옛 답이 달리는 것보다 답 없음이 낫다는 판단이다.
  이 경우 콘솔에 `[answer-mismatch] ... 질문 스냅샷이 현재 퀴즈 포인트와 달라
  답안을 숨겼습니다 — 스냅샷="..." / 현재="..."` 경고가 뜬다. **답안 파일의 `>`
  줄을 새 질문 문구로 갱신**하면 다시 나타난다(답안 본문을 다시 쓸 필요는 없다,
  질문이 사실상 같은 뜻이면).
- 답안 본문이나 스냅샷이 빈 문항은 건너뛰고 경고만 낸다.
- quiz.html에는 문항·배지와 (있으면) 이 답안 텍스트만 인라인한다. 표·인용·
  슬라이드·다이어그램을 포함한 전체 자료는 인라인하지 않고 개념 페이지로
  링크한다 — quiz.html은 "답안을 구성하는 연습" 용도라 원문 재현이 아니다.

## 데이터 파일 세 가지 — comparisons.yml / core-concepts.json / importance.json

이 셋은 서로 역할이 다르고 관리 빈도도 다르다.

### `importance.json`

개념별 시험 중요도(1~5점) + 근거 한 줄. `concepts["W01/5"]` 형태의 키로 찾는다.
없는 개념은 `default`(기본 3점)로 채워지고 경고가 뜬다. **쪽지시험 핵심개념
10에 뽑힌 개념은 여기 몇 점을 적어도 자동으로 5점으로 승격된다**(아래 참고) —
낮춰 적어도 소용없다.

### `core-concepts.json`

퀴즈 회차별 "핵심 개념 10개 안팎" 세트. 항목마다:
- `concepts`: 본체 개념(들) — 핵심 배지가 붙고 별점 5점으로 승격된다.
- `also`(선택): 함께 보면 좋은 개념 — 링크만 붙고 승격은 안 된다.

세트를 추가하는 절차(퀴즈 회차마다):
1. 그 회차 범위에서 핵심 개념을 추려 `개념정리/쪽지시험_핵심개념/`에 md로 쓴다.
   `## <번호>. <제목>` + 첫 blockquote 메타(주차/슬라이드/강의기록) 형식을
   지킨다. **번호 순서가 곧 공부 우선순위**이고 사이트가 그 순서를 그대로
   보여준다. md 본문은 빌드 시점에 렌더되어 HTML에 박히므로, 사이트 쪽에
   md 복사본을 따로 두지 않는다.
2. `core-concepts.json`에 세트를 추가하고(`quiz`/`id`/`label`/`file`/`items`)
   항목마다 `concepts`(+선택적 `also`)를 연결한다.
3. `node build.mjs`를 돌리면 `core.html`에 세트가 쌓이고, index.html의 학기
   지도에서 그 회차 버튼이 활성화된다.

### `comparisons.yml`

`map.html`의 "주차 간 비교표" 데이터. `INDEX.md`는 빌드가 직접 파싱하지 않으므로
(그 안의 "주차 간 비교 개념" 메모는 사람이 보는 기획 문서일 뿐), 비교표로 쓸
내용은 여기로 옮겨 써야 한다. 항목 하나:

```yaml
- id: X04
  title: 표 제목
  note: >
    이 표의 근거·한계를 적는다(예: 아직 안 쓰인 개념의 슬라이드 훅만 반영했다는 것).
  columns: ["항목", "W01/05 ...", "W02-2/05 ..."]
  rows:
    - ["층위", "...", "..."]
```

- `columns`/`rows` 셀에 `W##/NN` 표기(예: `W01/05`)를 쓰면, 그 개념이 이미
  작성돼 있으면 링크로, 아직 없으면 평문으로 남는다(`map.mjs`의
  `linkifyRefs`) — 존재하지 않는 앵커로 링크를 걸지 않기 위해서다. 개념이
  새로 쓰이면 다음 빌드부터 자동으로 링크가 된다(이 파일을 다시 고칠 필요
  없음).
- 이 파일이 파싱에 실패해도(YAML 문법 오류) 빌드는 죽지 않고 `[map]` 경고만
  내고 빈 비교표로 진행한다 — 문법 오류가 있으면 그 경고를 보고 고친다.

## 플래그

| 플래그 | 하는 일 |
|---|---|
| (없음) | 전체 빌드 |
| `--print-config` | 해석된 경로(config.json 병합 결과)를 출력 |
| `--dump-json` | 개념 파싱 결과를 JSON으로 출력 (페이지 생성 안 함) |
| `--check` | 빌드 후 생성된 HTML의 내부 링크·이미지·앵커를 전부 검증 |

`--check`는 항상 켜 두는 게 좋다(§ 한 줄 요약). 링크 체커(`lib/check.mjs`)가
검사하는 것과 하지 않는 것:

- 검사함: `<a href>`/`<img src>`/`<script src>`/`<link href>`가 가리키는 내부
  파일의 존재, `#앵커`가 가리키는 대상 페이지(또는 같은 페이지)의 실제 `id`
  존재. 외부 링크(`https:`, `mailto:` 등)는 건너뛴다. `quiz.html?week=W01&c=c01`
  같은 쿼리 스트링은 `?` 앞 파일명만으로 판단한다(쿼리를 파일명으로
  오인하지 않는다).
- quiz.html/map.html은 `<script type="application/json">`에 데이터를 심어두고
  클라이언트 JS가 그걸로 DOM을 그린다(퀴즈 답안 링크, 그래프 노드 href 등).
  이 JSON은 "라이브 DOM이 아니다"라서, 체커는 이걸 페이지 본문과 분리해 따로
  다룬다: JSON의 `href`/`src` 값과, 그 안에 렌더된 답안 HTML에 박힌
  `<a href>`는 실제로 존재하는 파일/앵커인지 검사하지만(답안 마크다운 링크가
  깨지면 여기서 잡힌다), JSON 안의 순수 프래그먼트(`#top`처럼 파일명이 없는
  링크)는 검사하지 않는다 — 그게 가리킬 DOM은 클라이언트 JS가 렌더링을 마친
  *뒤*에만 생기고, 정적 HTML을 읽는 이 체커는 그 시점의 DOM을 알 수 없기
  때문이다. JSON의 `id` 키(예: 문항 id `"W01/c01/0"`)는 페이지의 진짜 `id`
  집합에 넣지 않는다 — 안 그러면 그 값이 실제 DOM에 없는데도 있는 것처럼
  오판(거짓 음성)할 수 있다.

**`node --test test/`(디렉터리를 직접 지정)는 쓰지 않는다** — 이 macOS의 Node

## 알려진 사항 (버그가 아니다)

- **`sips`는 macOS 전용이다.** 슬라이드 이미지를 JPEG로 변환하는 데 macOS
  내장 `sips` 커맨드를 쓴다(`lib/images.mjs`). 다른 OS에서는 이미지 처리
  단계가 실패하거나 원본을 그대로 복사한다 — 이 도구는 이 맥북에서 돌리는
  걸 전제로 한다.
- **`config.json`의 경로가 이 맥북에 묶여 있다.** `conceptDir`/`assetDir`가
  Google Drive의 절대경로(`/Users/yenarue/Library/CloudStorage/...`)다. 다른
  기기에서 쓰려면 이 두 경로를 그 기기 기준으로 고친다.
- **`file://`로 직접 열면 검색이 꺼진다.** 사이트를 로컬 파일로 그냥 열면(포트
  없이 더블클릭) `fetch('search-index.json')`가 대부분 브라우저에서 실패한다
  (`file://` 문서의 로컬 파일 fetch 제한). `assets/js/main.js`가 이를 감지해
  검색창에 "파일로 직접 열면 검색이 안 된다"는 안내만 보여주고 조용히
  넘어간다 — 버그 아님. 검색까지 확인하려면 `python3 -m http.server`처럼
  로컬 서버로 띄워서 열어야 한다.
- **`[related]` 경고 10건은 정상이다.** W02-2(지식의 공공성 논쟁, 9/19 강의
  예정)의 개념 3~4개를 아직 안 써서, 그걸 참조하는 W01/W02-1/W02-2의 다른
  개념들이 "대상 개념이 아직 없습니다" 경고를 낸다. W02-2가 다 채워지기 전까지
  이 경고 개수는 그대로 10건이어야 하고, 늘거나 줄면 원인을 봐야 한다(새
  `related` 참조를 추가했는데 오타가 났거나, W02-2 개념을 채웠는데도 경고가
  안 줄면 `parseRelatedRef`가 그 표기를 못 읽는 것).
- 사이트는 `<meta name="robots" content="noindex,nofollow">`와
  `robots.txt`(`Disallow: /`)로 검색 색인은 막지만, **URL을 아는 사람은 볼 수
  있다.** 강의 슬라이드 캡처와 교수 발언 직접 인용이 포함돼 있으니 URL을
  함부로 공개하지 않는다.

## 설계 문서

전체 설계(§ 데이터 모델, 페이지별 요구사항, 파일 구조 등)는 Google Drive의
`개념정리/web/PRD.md`에 있다. 이 README는 "PRD를 다 잊었을 때 일단 돌리는 법"
용도이고, 설계 이유가 궁금하면 PRD를 본다.
